## 🏗️ Архітектура Системи
Сервіс побудований на тріаді **React + Firebase + Gemini (REST)**.

1. **Frontend (Vite + Zustand)**: Керує станом проекту та історією. 
   - [Критично] `useProjectState.ts` — синхронізує локальний стан зі стором Firestore.
2. **Backend Proxy (Cloud Functions v2)**: Функція `api` (Node.js 22).
   - [Чому так] Ми використовуємо функцію як проксі до Google API, щоб **приховати API Ключі** та уникнути CORS-проблем.
3. **AI Engine (Gemini REST v1)**: Прямі HTTP-запити до Google.
    - [Стабільність] Використовується **Native JSON Mode** (`responseMimeType: "application/json"`). Це гарантує структуру без збоїв та видаляє потребу у важкому парсингу.

## 🧠 Робота з Gemini API (v1)

### 1. Версійність та Моделі
- **Версія API**: Використовуйте тільки **`v1`** (стабільна).
- **Динамічна модель**: Модель НЕ захардкоджена. Вона береться з `process.env.GEMINI_MODEL`.
- **Поточний дефолт**: `gemini-2.5-flash`.

### 2. Гарантована стабільність JSON (Native Mode) 🛡️
Ми перейшли на нативну підтримку JSON у Gemini API:
1. **JSON Mode**: Вказано `responseMimeType: "application/json"` у конфігурації запиту.
2. **Auto-Retry**: Система автоматично робить повторну спробу при помилках парсингу або мережі.
3. **8k Limit**: Промпти містять обмеження до 8000 символів для уникнення обривів тексту.

### 3. Трюк "Legacy Style" (Double Prompt) ✨
Щоб зберегти високу якість генерації "як раніше" при переході на REST API, ми використовуємо структуру **двох частин (parts)** в одному повідомленні. Це імітує розділення на "Систему" та "Користувача", даючи моделі подвійний фокус на контексті.

## 🔐 Керування Секретами (Secrets)
Ми НЕ використовуємо `.env` для ключів у продакшені. Все зберігається у **Secret Manager**.

**Основні команди:**
- `firebase functions:secrets:list` — глянути список.
- `firebase functions:secrets:set GEMINI_MODEL` — змінити модель "на льоту".
- `firebase functions:secrets:set GEMINI_API_KEY` — оновити ключ.

## 🚀 Нюанси Деплою та "Примарні баги"

### 🛡️ Трафік (Pinned Traffic)
Якщо після деплою ти бачиш старий код — **перевір розподіл трафіку** у Google Cloud Run. 
- **Фікс**: `gcloud run services update-traffic api --to-latest --region us-central1`.

### 🚑 Діагностика (Health Check)
Для швидкої перевірки роботи бекенду без фронтенду використовуй:
`https://whitewrite.com/api/health?diag=true`
Це посилання перевірить:
1. Авторизацію.
2. Доступ до секретів.
3. Прямий "пінг" до Gemini API.

## 🛠️ Поради для Масштабування
1. **Save Queue (Черга збереження)**: Авто-сейв реалізовано через **Sequential Promise Queue** у `useStoryStore.ts`.
   - Жодних race conditions: кожен запис чекає на завершення попереднього.
   - Версіонування: старі версії пропускаються, якщо вже є новіший snapshot.
2. **UI Feedback**: Стан `isSaving` та `isDirty` виведено у хедер для візуального контролю.
3. **Аудіо**: TTS (Text-to-Speech) використовує окремий Google API ключ, що також лежить у секретах.

## 🛠️ Архітектура Збереження (Support Guide)

### 1. Потік Даних (Data Flow)
`User Action` → `Update UI` → `structuredClone(Snapshot)` → `Enqueue(Queue)` → `Firestore Write` → `Clear isDirty`.

### 2. Гарантії
- **Zero Race Conditions**: Завдяки черзі `saveQueue`, запити обробляються строго один за одним.
- **Snapshot Integrity**: Система передає в Firebase копію даних на момент дії, а не живий об'єкт.

### 3. Відладка (Debug)
- **Консоль (F12)**: Шукайте логи з префіксом `[SAVE_QUEUE]`.
- **Zustand State**: Слідкуйте за `currentSaveVersion` (інкрементується при дії) та `isSaving`.
- **Мережа**: Якщо індикатор у хедері став червоним (`saveError`), перевірте Firestore connection.
